# 行为生成器统一重构方案

> 历史文档：当前执行链路已于 2026-10-09 调整，请以[事件驱动大脑与资源订单](事件驱动大脑与资源订单.md)和源码为准。本文的日程、昼夜权重、执行节流与部分待办状态可能已失效。

> 状态：**方案待确认**。目标：删除"每日定死计划"这路反模式，把散落的三套目标生成器收敛成**单一行为生成器**，按来源分三类，且 routine 任务改为"持久、完成后降权、不删除、可多次做"。

---

## 一、现状问题（为什么重构）

日志诊断（`E:\mc\...\1.16.5-Forge_36.2.42\logs\latest.log`）已确认三个根因：

1. **三套生成器互相打架**：`VillagerSchedulePlanner`（每日计划 `src=routine_dawn`）+ `RoutineScheduler`（`src=repeatable:seed`）+ `VillagerAgentManager.generateNewGoals`（`src=fallback_random`）同时在列表里填 ONE_SHOT 目标，造成"注入→秒完成→移除→再注入"抖动，村民永远在选目标空转，从不落地成持续移动。
2. **每日定死计划是反模式**：`DailySchedule` 把一天切成 morning/afternoon/evening/night 四个固定时间槽。这和"按当前状态 + 时间权重选任务"的模型根本冲突（架构反思文档早就说要干掉它，代码没跟）。
3. **死目标**：`restock` 对无业/无工作站村民是 NOHANDLER（`RestockSkill.canHandle` 因无 JOB_SITE 返回 false），但它是 REPEATABLE 永远在列表里空转。

## 二、目标架构：单一行为生成器，按来源分三类

```
                        ┌─────────────────────────────────────────────┐
                        │        BehaviorGenerator（统一入口）          │
                        └─────────────────────────────────────────────┘
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
┌───────────────────┐       ┌────────────────────┐       ┌──────────────────────┐
│ 类型1 目标驱动      │       │ 类型2 日常任务(Routine)│       │ 类型3 事件触发(Reactive)│
│ Goal-Driven       │       │ 持久·降权·不删除     │       │ 短命·一次性·高优先     │
├───────────────────┤       ├────────────────────┤       ├──────────────────────┤
│ 父目标的前置未满足  │       │ 主业(职业池)         │       │ 遇怪 → 战斗(combat独占) │
│  → 生成前置子目标   │       │ 爱好(能力池)         │       │ 威胁 → 集结(SignalBoard)│
│    · 缺材料→craft  │       │ 加权采样 + 相位权重   │       │ 新村民 → socialize      │
│    · 缺工具→restock│       │ 完成后降权(冷却)      │       │ 作物成熟 → farm 提权     │
│    · 无工作站→找工作 │       │ 同一天可多次做       │       │ (WorldEventBus)         │
└───────────────────┘       └────────────────────┘       └──────────────────────┘
        │                               │                               │
        └───────────────────────────────┼───────────────────────────────┘
                                        ▼
                           统一目标漏斗 AgentGoal[]
                                        ▼
                     GoalScheduler（仲裁，本轮不动）→ Skill 执行
```

**三条铁律**（消除三套打架的根子）：

1. **每个 goal 只能有一个来源**（`GoalSource` 明确标记 GOAL_DRIVEN / ROUTINE / REACTIVE），不允许两套生成器写同一种 goal。
2. **类型2 是唯一常驻生成器**：routine 目标是"村民能做的事的候选集"，永远在列表里，靠权重 + 冷却 + 相位被选中，**绝不删除、绝不每天重建**。
3. **类型1 和 3 只产生"有父目标/有事件"的短命目标**，父目标完成/事件过期即消失，绝不自己常驻。

## 三、类型2（Routine）—— 核心重定义

### 3.1 语义

| 属性 | 旧（DailySchedule / fallback） | 新（Routine） |
|------|-------------------------------|---------------|
| 生命周期 | ONE_SHOT，黎明重建 | **REPEATABLE，永不删除** |
| 注入时机 | 每天黎明 | **职业变化时**注入（获得职业 → 注入对应主业 + 已有爱好） |
| 完成后 | 移除 | **降权/进冷却**，同一天内可再次被选中（间隔由冷却决定） |
| 内容 | 定死时间槽 | 职业池 ∪ 能力池（"村民会做的事"） |

### 3.2 权重模型（复用现有 `DeterministicPlanGenerator` 的池，改输出）

```
routine goal = 职业池 ∪ 能力池（并集）
  职业池：farmer→farm(5) socialize(2)；smiths→craft(5) socialize(2)；无业→wander(2)
  能力池：额外解锁的爱好（会钓鱼→fishing；会采集→gather），权重 = base × (1 + 0.3×level)
```

- **每个 routine 目标带**：`priority`（日常带 2–6）、`dayWeight/nightWeight`（工作类白天有权重、夜间 0）、`cooldownTicks`（完成后冷却多久可再做）。
- **"完成后降权"落地为 cooldown**：skill 返回 SUCCESS → REPEATABLE goal 复位 `completed=false`，但写入 `cooldownUntilTick = now + cooldownTicks`。冷却期内 `GoalScheduler` 不选它（现有逻辑已支持），冷却结束自动恢复可做 → **同一天可多次做，但不会连续刷**。
- **不删除**：`RoutineScheduler` 只负责"缺失则补种"，永不 evict；`expireGoals` 对 REPEATABLE 永不删（现有逻辑已保证）。

### 3.3 内容改动

- `DeterministicPlanGenerator` 的 `generateRoutineGoals`：**去掉 `GOALS_PER_DAY=3` 和 ONE_SHOT**，改为生成 REPEATABLE 目标集合（每个职业/能力一项），交给 `RoutineScheduler` 幂等补种。farm 的特殊处理（由 `RoutineScheduler` 独占、排除 daily 注入）保留。
- `RoutineScheduler`：`REPEATABLE_TYPES` 从硬编码 `{farm, restock, rest, wander}` 改为**由职业/能力池动态派生**；`rest`（睡觉）和 `wander`（兜底）作为**无条件的通用 routine**保留。

### 3.4 restock 门控（类型2 内的特例）

`restock` 改为**有职业且已认领工作站才种**：

```
seed("restock"):
  if 无职业 or 无 JOB_SITE memory → return null（不种）
  else → 种 restock routine（dayWeight 正常）
```

这样无业村民的 restock 死目标从源头消失。

## 四、类型1（Goal-Driven）—— 前置子目标

**触发**：一个正在运行的目标卡在"前置未满足"（BLOCKED + 可恢复的 FailureReason），不是删父目标，而是**生成一个服务它的前置子目标**。

现有 `FailureRecoveryPlanner` 已经是这个模式的正确雏形，统一收编。它读 `AgentGoal.lastFailure`（`FailureReason` + `Failure` 载荷），**按失败类型分派**：

```
父目标缺 X（MISSING_ITEM）
  ├ 已有目标能产出 X → 提权（去重，扫 outcomeItems）
  ├ 能合成 → 生成 craft 子目标（材料递归 ≤2）
  └ 不能 → 广播求购（TRADE_WANT）
```

**完整失败类型 → 反应分派矩阵**（本次重构要补全的，现状只有前两行有真反应）：

| FailureReason | 现状反应 | 重构后反应 |
|---|---|---|
| `CAPABILITY_TOO_LOW` | 只写记忆 | 不变（必须升级能力，无法用物品恢复） |
| `MISSING_ITEM` | 三步链（已有 todo→craft→trade） | 不变 |
| **`NO_JOB_SITE`** | **只写记忆（死路）** | **新增：注入 `find_job_site` 前置子目标（POI 找工作站点）** |
| **`NO_RECIPE`** | **只写记忆（死路）** | **新增：回落交易——直接发 `TRADE_WANT`（没配方 = 最该去换）** |
| `NO_BED` / `BED_OCCUPIED` / `NOT_NIGHT` | 只写记忆 | 不变（等天亮 / 建床） |
| `UNREACHABLE` | 只写记忆 | 不变（v1 不加重试，交给 abandonRunningGoal 冷却后重试） |
| `UNKNOWN` | 只写记忆 | 不变（生产者 bug，留日志） |

**两条新分支是这次重构的第一刀**：
- **`NO_JOB_SITE` → `find_job_site`**：RestockSkill/CraftSkill 在 `canHandle` 过了（有职业）但执行时发现 `JOB_SITE` 丢了（工作站被拆）→ 之前只记一条"stalled"记忆就放弃，村民原地不动。现在注入 `find_job_site` goal（用原版 POI 系统 48 格内重找工作站），认领后 `JOB_SITE` 恢复、routine restock 自动接上。
- **`NO_RECIPE` → 回落交易**：AcquireItemSkill 对"无配方物品"返回 `NO_RECIPE`，之前不恢复。但"没配方"恰恰最该走交易——改为与 `MISSING_ITEM` 共用第三步（`postTradeWant`），去重靠 `recoveryKey()`（`reason:itemId`），不会重复发。

**语义约束**：子目标带 `GoalSource.GOAL_DRIVEN`（类型1），父目标完成/取消时子目标自动失效（避免孤儿目标常驻）。

## 五、类型3（Reactive）—— 事件触发

**不改战斗系统**（combat 是 `VillagerAgentManager.tickCombat` 独占，正确，不动）。类型3 只覆盖"事件 → 一次性目标"：

| 事件 | 目标 | 来源 |
|------|------|------|
| 遇怪（威胁出现） | 战斗/逃跑（combat 独占，不进漏斗） | `tickCombat` |
| 威胁集结 | `defend`（SignalBoard） | 已有 |
| 新村民加入 | `socialize`（一次性） | `WorldEventBus`（已接） |
| 作物成熟 | `farm` 提权 + targetLocation | `WorldEventBus`（**待接**） |
| 掉落物 | `pickup` | 已有 `ItemAttractionSystem`（收编为 goal，待接） |

语义：**短命、高优先、一次性**。事件过了就消失，不常驻。

## 六、找工作站点 —— 改用原版 POI 系统

### 6.1 原版怎么做（已核实）

原版 Java 村民找工作**不扫方块**，而是用 **兴趣点管理器（PointOfInterestManager）**：

1. 无业村民（非 baby/nitwit）在 **48 格球体**内查最近的、**未认领**的 `acquirable_job_site` 类型 POI（`findClosest(type, pos, radius, status)`，O(1) 索引查询）；
2. 写入 `POTENTIAL_JOB_SITE` memory，`WalkTowardsJobSiteTask` 走过去（**临时认领**，60 秒到不了释放但可重试）；
3. 走进 **2 格半径** = 完全认领 → 职业改变 + 绿粒子，`POTENTIAL_JOB_SITE` 抹除、`JOB_SITE` 写入；
4. 工作方块被破坏 → `LoseJobOnSiteLossTask` 立即抹 `JOB_SITE`；
5. 只在清醒时执行。

关键：原版用 `world.getPointOfInterestManager()` + `PointOfInterestType`（每个工作站方块是一个注册 POI），而不是手写 16 半径扫描。

### 6.2 我们的落地

- **删除** `VillagerEventHandler.assignNearestJobSite` 的手写扫描。
- **新建** `FindJobSiteSkill`（实现 `VillagerSkill`），处理 `find_job_site` 目标：
  1. `canHandle`：无 `JOB_SITE` 且是成年无业村民；
  2. `execute`：`world.getPointOfInterestManager().findClosest(type, pos, 48, Occupancy.HAS_SPACE)`（type 由目标职业决定，无业则任意 acquirable 类型）；
  3. 找到 → `POTENTIAL_JOB_SITE` + 走过去（复用 `driveMoveGoal`）；
  4. 到达 2 格 → 认领：写 `JOB_SITE`、`updateProfession`、**触发 routine 注入**（§三 3.1 的"职业变化时注入"）；
  5. 找不到 → 降权/放弃，交给 wander。

## 九、边界情况

1. **能力为空的无业村民**：类型2 只剩 `wander`（无条件兜底）→ 永远有事做（解决"完全不动"）。
2. **routine 完成瞬间又冷却结束**：冷却由 `cooldownTicks` 保证最小间隔，不会连续刷同一行为。
3. **职业中途丢失**（工作站被拆）：`JOB_SITE` 丢失 → 类型1 重新生成 `find_job_site` 前置 → 找回或换岗。
4. **LLM 离线**：类型2/3 全部确定性，不依赖 LLM；LLM 仅通过 `HarnessDecisionPlanner` 追加一条校验过的目标（类型3 的一种，保持现状）。

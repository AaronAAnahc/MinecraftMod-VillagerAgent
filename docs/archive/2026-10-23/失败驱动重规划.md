# 失败驱动重规划（Failure-Driven Re-planning）

> 一句话：**每个 todo 启动失败时记录一个「预定义失败原因」，规划器按原因注入补救 todo（缺锄头→获取锄头，缺物品→合成/交易），并外扩到所有 todo 的前置条件失败。**
>
> 状态：设计稿，**待确认后实现**。

---

## 1. 目标与动机

现状：`FarmSkill` 里 `ensureFarmerHoe()` 让农民**原地凭空**获得铁锄——这是用户明确否决的。正确行为应是：农民**意识到自己没有锄头**，然后走一条确定性的补救链（去工作方块补货 → 自己合成 → 在村庄发交易需求）。

把这条补救链抽象成通用系统：

1. **失败可观测**：每个 todo（goal）启动/执行失败时，用一个**预定义枚举**记录失败原因，而不是静默跳过或硬编码兜底。
2. **失败可恢复**：一个 `FailureRecoveryPlanner` 按「原因 → 处理方式」映射表，注入补救 todo 或调整已有 todo 优先级。
3. **通用化**：同一套机制覆盖「缺工具 / 缺物品 / 缺能力 / 无工作方块 / 无配方 / 不可达」等所有前置条件失败，而非只给锄头开小灶。

对齐既有架构（详见 `working_memory` 的「统一目标漏斗」）：世界只有一种「现在要做什么」= `AgentGoal` 列表，按 `priority`/`weight` 仲裁。本系统**不改架构**，只新增「失败 → 新 goal」的生成器与若干新 skill。

---

## 2. 核心概念

### 2.1 失败发生的两个时机

| 时机 | 现状 | 新行为 |
|---|---|---|
| **前置失败**（`canHandle` 返回 false） | 只打一行 `No skill handles goal type` | 无 handler 时，由 skill 自报 `FailureReason`（`diagnose`），或由 executor 用 goal 自带原因兜底 |
| **执行失败**（`execute` 中途无法继续 / 返回 `BLOCKED`/`FAIL`） | `BLOCKED` 累积后直接放弃 | 失败原因写到 `goal.lastFailure`，交给 planner |

关键点：**「缺锄头」不是 farm goal 整体失败**——农民仍能收割/播种。它是 farm 内部 **till 步骤的前置缺失**。因此失败上报应发生在 skill 内部某一步无法进行时，而非只有 goal 失败才报。

### 2.2 设计原则

- skill 单例、不存村民状态（既有约定）→ 失败原因写进 **`goal`**（每村民每 goal 独立），不进 skill。
- 规划器纯确定性、无 LLM（与 `BehaviorExecutor` 同层）。
- 补救 todo 必须**去重**，防止 routine goal 每 tick 自愈重建 → 反复触发 → 刷屏。
- 交易需求复用现有 `VillageSignalBoard`（`TRADE_WANT`/`TRADE_HAVE` 消息总线，已有 TTL + 去重 + 撮合）。

## 3. 数据模型

### 3.1 `FailureReason`（预定义枚举，`ai/behavior/FailureReason.java`）

```java
public enum FailureReason {
    MISSING_TOOL,        // 缺工具（锄/斧/剪/钓竿…），itemId = 工具
    MISSING_ITEM,        // 缺材料/种子/燃料等可持有物，itemId + quantity
    CAPABILITY_TOO_LOW,  // 能力等级不足，capability + requiredLevel
    NO_JOB_SITE,         // 无工作方块（无法补货/合成）
    NO_RECIPE,           // 目标物无可用配方
    NO_BED,              // 无可用床（睡眠类）
    BED_OCCUPIED,        // 床被占用
    NOT_NIGHT,           // 非夜间（睡眠类，通常直接结束不补救）
    UNREACHABLE,         // 寻路不可达
    UNKNOWN              // 兜底
}
```

### 3.2 `Failure`（失败记录，`ai/behavior/Failure.java`）

```java
public final class Failure {
    public final FailureReason reason;
    public final String itemId;          // 可空：缺的工具/物品 registry name
    public final int quantity;           // 缺的数量（默认 1）
    public final CapabilityId capability; // 可空：能力不足时用
    public final int requiredLevel;
}
```

### 3.3 `AgentGoal` 新增字段

```java
private Failure lastFailure;          // 最近一次失败（executor 写入，planner 读取）
public Failure getLastFailure();
public void setLastFailure(Failure f);
```

（不 NBT 持久化——失败是运行时信号，重进游戏后 routine 会重新触发。）

### 3.4 复用的既有能力

| 能力 | 位置 | 用途 |
|---|---|---|
| `AgentInventory.countItem/addItem/removeItem` | `VillagerAgentData` | 判断/增减物品 |
| `NativeRecipeResolver.resolveRecipe(world, itemId)` | — | 判断「可合成」+ 取材料 |
| `ResolvedRecipe.consumeAndProduce` | — | 实际合成 |
| `SkillCraftCatalog.isUnlockedFor(pool, prof, item)` | — | 能力门控合成 |
| `VillageSignalBoard.post/hear/matchTrade/resolveTrade` | 消息总线 | 发布/撮合交易需求 |
| `VillagerAgentData.lastRestockTime` / `restockAtJobBlock()` | — | 补货判定与执行 |

## 4. 失败原因 → 处理方式 映射表（核心）

> 用户要求：对每个失败情况写一个处理方式。下表即「每种失败原因的处理器」。

| FailureReason | 触发场景（谁上报） | 处理方式（planner） |
|---|---|---|
| `MISSING_TOOL` | FarmSkill till/maintain 无锄头；牧羊人无剪等 | 见 §5.1 工具获取专案（补货→合成→交易） |
| `MISSING_ITEM` | CraftSkill 缺材料；FarmSkill 无种子；fuel 不足 | 见 §5.2 缺物品专案（找已有 todo → 新建 acquire_item） |
| `CAPABILITY_TOO_LOW` | 任何 `passesCapabilityGate` 不过 | 不补救；goal 标记 BLOCKED 保留（等升级），记 memory |
| `NO_JOB_SITE` | Restock/Craft 无 `JOB_SITE` 记忆 | 跳过补货/合成，直接走交易（TRADE_WANT） |
| `NO_RECIPE` | Acquire/Craft 找不到配方 | 跳过合成，直接 TRADE_WANT |
| `NO_BED` | SleepSkill 无可用床 | goal 保留稍后重试；连续失败记 memory「村中无床」 |
| `BED_OCCUPIED` | SleepSkill 床被占 | 重解析下一张床；无则退化为 `NO_BED` |
| `NOT_NIGHT` | SleepSkill 白天被调 | 直接结束 goal（已有逻辑），不补救 |
| `UNREACHABLE` | 寻路失败 | 记 memory，goal 换目标或放弃 |
| `UNKNOWN` | 兜底 | 打日志，goal 保留 |

## 5. 两个专案流程（用户给定优先级）

### 5.1 工具获取专案（`MISSING_TOOL`，如锄头）

按优先级依次：

1. **补货可做？** 若「今日未补货」（`lastRestockTime` 距今 ≥ 24000）且本职业 starter items 含该工具（`JobStarterItems`）→ **提升 restock todo 的 priority**（+3）。
2. **能自己合成？** 若 `NativeRecipeResolver.resolveRecipe(tool) != null` 且 `SkillCraftCatalog.isUnlockedFor(pool, profession, tool)` → **新增 craft todo**（`targetItem = tool`）。
3. **否则购买**：在 `VillageSignalBoard` 发布 `TRADE_WANT(tool)`（已有撮合会有人来卖）。

### 5.2 缺物品专案（`MISSING_ITEM`，如种子/铁锭）

1. **找已有 todo**：遍历现有 goals，若存在能获得该物品的 todo（`craft`/`gather`/`trade` 且 `targetItem == item`，或 `acquire_item`）→ **提升其 priority**（+3）。
2. **否则新建 `acquire_item` todo**（见 §6.2）。

### 5.3 `AcquireItemSkill` 获取物品流程（用户给定）

1. **尝试合成**：可合成 && 已解锁 && 材料齐 → `consumeAndProduce` → `SUCCESS`。
2. **否则发布该物品交易需求**：`TRADE_WANT(item)`（若未发过）。
3. **否则发布合成材料的交易需求**：对每个缺失材料发 `TRADE_WANT(material)`（递归 bootstrap）。
4. **完成移除**：`acquire_item` todo 完成后，`resolveTrade` 移除它发布的材料需求。

## 6. 新增 goal 类型与 skill

### 6.1 `restock`（去工作方块补货）— `RestockSkill`

- **goalType**：`"restock"`
- **routine**：新增早间窗口注入（`RoutineScheduler`），如 `06:00–12:00` 每村民一次。
- **canHandle**：`JOB_SITE` 记忆存在，且今日未补货（`lastRestockTime` 距今 ≥ 24000）。
- **execute**：走到 `JOB_SITE`（复用 `driveMoveGoal` 的走-到达模式）→ 到站后 `agent.restockAtJobBlock()` → 记 `lastRestockTime` → `SUCCESS`。
- **失败上报**：无 `JOB_SITE` → `NO_JOB_SITE`。

> 与现有 `checkJobBlockRestock`（被动：恰好路过才补货）关系：本系统把补货提升为**显式 goal**。保留被动检查作为「路过顺手补货」的廉价加成，二者共用 `restockAtJobBlock()` + `lastRestockTime`，不冲突。

### 6.2 `acquire_item`（获取物品）— `AcquireItemSkill`

- **goalType**：`"acquire_item"`，`targetItem` = 目标物，`targetQuantity` = 数量。
- **lifecycle**：`ONE_SHOT`（到手即完成并移除，不复生）。
- **canHandle**：`targetItem` 非空。
- **execute**：走 §5.3 三步；每 tick 检查 `countItem(targetItem) >= quantity` 时 → 移除材料需求 → `SUCCESS`。
- **失败上报**：无可合成配方 → `NO_RECIPE`（此时继续走交易，不算终态失败）。

## 7. 端到端场景

### 场景 A：农民无锄头（本次主诉）

1. `day_farm` 窗口注入 `farm` goal。
2. `FarmSkill.execute` 收割/播种正常；进入 till 步骤发现 `hasHoe()==false` → `goal.setFailure(MISSING_TOOL, wooden_hoe/iron_hoe)` → 完成本轮（能做的做完）或 `BLOCKED`。
3. executor → `FailureRecoveryPlanner.handle`：
   - farmer starter items 含 `iron_hoe`，今日未补货 → **提升 `restock` priority**。
4. `RestockSkill` 走到堆肥桶 → `restockAtJobBlock()` → 拿到 `iron_hoe` + 种子。
5. 下个 farm 周期 till 成功。日志出现 `tilled …`。

### 场景 B：农民无种子

1. farm 播种步骤 `hasSeeds()==false` → `MISSING_ITEM(wheat_seeds)`。
2. planner：现有 todo 无产种子的 → 新建 `acquire_item(wheat_seeds)`。
3. `AcquireItemSkill`：种子无配方 → 发布 `TRADE_WANT(wheat_seeds)`。
4. 别的 farmer 有盈余（economy scan 已发 `TRADE_HAVE`）→ 撮合 → 交换 → todo 完成。

### 场景 C：铁匠缺铁锭合成铁剑

1. `craft(iron_sword)` 的 `CraftSkill` 缺 `iron_ingot` → `MISSING_ITEM(iron_ingot)`。
2. planner：新建 `acquire_item(iron_ingot)`。
3. `AcquireItemSkill`：铁锭可合成（铁矿/铁块/铁粒）→ 材料齐则合成；否则发布 `TRADE_WANT(iron_ingot)` + 缺材料的 `TRADE_WANT`。

## 9. 边界与错误处理

- **去重防刷**：同一 `(villager, reason, itemId)` 的补救 todo 只注入一次；routine goal 自愈重建不重复触发（用「是否已存在同类补救 todo」判断，而非时间）。
- **交易需求 TTL**：`VillageSignalBoard` 已有 TTL + `post` 去重，超时自动消失；planner 不重复发。
- **循环依赖**：A 缺 B、B 缺 A 时，材料需求递归**限深 2 层**，超过则停在交易需求层（不再往下拆材料），防死循环。
- **无交易对手**：`acquire_item` todo 挂着等（`EXPIRING` + deadline），超时记 memory 放弃；routine 下一天再触发。
- **能力不足**（`CAPABILITY_TOO_LOW`）：不注入补救，goal 保留；靠 `SocializeSkill` 拜师/升级后自然解锁。
- **失败上报线程安全**：全部发生在 server thread 的 `processGoals` 内，无并发问题。

## 10. 不做的事（Out of Scope）

- 不做通用 HTN/GOAP 规划器——只做「失败 → 补救」这一层，确定性、无 LLM。
- 不做多步承诺型任务（如「去箱子取回 X 再回来」）——那类套 `FarmReclaimState` 的显式相位模式（既有结论）。
- 不做价格博弈/讨价还价——交易仍按现有价值表撮合。
- 不改 `GoalScheduler` 的仲裁算法——只通过 priority 升降引导。
- 交易需求仅村庄范围（既有 48 格听觉半径），不做跨村。

## 12. v2 实现记录（2026-08-22）

### 关键精简（vs v1 设计稿）

- **工具/物品统一**：`FailureReason` 无 `MISSING_TOOL`，只有 `MISSING_ITEM`（工具 = 物品，`itemId` 存 registry name）。同一套三步链处理两者。
- **`outcomeItems` 字段**：每个 goal 记录预期获得物品集合。`restock` goal 的 outcome = 该职业 starter items（含 `iron_hoe`）——这是让 planner 能「缺锄头 → 发现 restock goal 可提供锄头 → boost restock」的关键。
- **删 `checkJobBlockRestock`**：被动补货删除，补货变显式 `restock` goal（RoutineScheduler 早间注入 + planner fail 时 boost）。

### 端到端流程（farmer 无锄头，本次主诉）

```
day_farm 窗口 → RoutineScheduler 注入 restock(priority 3, outcome={iron_hoe,...}) + farm(priority 5)
  → GoalScheduler 选 farm（priority 5 > 3）
  → FarmSkill: 收割/播种 OK；到 till 步骤 hasHoe==false
    → goal.setLastFailure(MISSING_ITEM, "minecraft:iron_hoe") → return BLOCKED
  → processGoals BLOCKED(streak==1) → FailureRecoveryPlanner.handle
    → step 1: 扫 goals，发现 restock.produces("minecraft:iron_hoe") 且 findHandler!=null
      → boost restock priority 3→6
  → 下 tick: restock priority 6 > farm 5 → 选 restock
    → RestockSkill: 走到 composter → restockAtJobBlock() → 拿到 iron_hoe → SUCCESS
  → 再下 tick: farm 重新选中 → till 成功 → log: "tilled …"
```

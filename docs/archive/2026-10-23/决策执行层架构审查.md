# 决策/执行层架构审查（为什么村民可能"不干活"）

> 历史文档：当前执行链路已于 2026-10-09 调整，请以[事件驱动大脑与资源订单](事件驱动大脑与资源订单.md)和源码为准。本文的日程、昼夜权重、执行节流与部分待办状态可能已失效。

> 状态：**A1 / A2 已修（2026-09-29）**，B/C 级待修。触发：用户质疑"skill 的 execute 每帧调用 = 把村民每帧行为替换为 skill 内容？"并要求一次性找全"决策/任务执行层导致不能运行的问题"，产出反思文档 + skill 自检清单。
> 结论先给：**execute 不是每帧调用，是 5 秒一次的离散决策脉冲；村民身体靠原版导航系统连续执行**。这个"离散决策 + 委托导航"的模型本身没问题，但有 6 个真实缺陷，其中 2 个会导致村民"在死目标上空转"，是"不干活"的结构性根因。

---

## 一、纠正一个模型误解：execute 不是每帧调用

**真实执行时序**（以代码为准，2026-09-29 核实）：

```
服务端 WorldTickEvent（每帧）
  └─ tickAgents()                每帧，但内部按村民节流
       └─ if (gt - lastThinkTime >= AGENT_THINK_INTERVAL=100 tick=5s)
            └─ updateAgent() → processGoals()
                 └─ GoalScheduler.pickNextGoal()     选 goal
                 └─ if (dispatchDue) skill.execute()  5s 一次
                      └─ agent.setCurrentAction(MOVE)
                      └─ villager.getNavigation().moveTo(...)  ← 委托原版导航
  └─ tickCombat()                每帧（战斗独立）
  └─ tickBuilding()              每帧（建筑独立）
```

- **`skill.execute()` 实际每 5 秒调一次**，不是每帧。因为 `processGoals` 只在 `AGENT_THINK_INTERVAL=100`（5 秒）的 think tick 里被调用，而 `BEHAVIOR_EXECUTOR_INTERVAL_TICKS=20` 的节流被这个更大的间隔**完全遮蔽**（`dispatchDue = gt - lastExecutorTick >= 20`，而 `gt - lastExecutorTick` 恒等于 100）。
- **村民身体的移动**不是 skill 每帧写的，而是 skill 里 `getNavigation().moveTo(...)` 设定了导航目标后，**原版导航系统每帧推进**。
- **原版 brain 被 mixin 抑制**：`VillagerEntityMixin.customServerAiStep` 在 `isAgentActive`（`currentAction != null`）时 `ci.cancel()`，防止原版 WORK/IDLE/REST 行为抢走导航。

所以等价说法是：**村民行为 = 「5 秒一次的离散决策脉冲」+「原版导航的连续执行」**。skill 是"决策器 + 导航目标设定器"，不是"每帧的身体驱动"。

## 二、问题清单（按严重度分级）

### A 级 —— 会导致"不干活"的结构性缺陷（必须修）

**A1. ✅ 已修（2026-09-29）`scheduledActivity` 链路已死，但 mixin 抑制契约还残留死分支**

> 修复：`VillagerEntityMixin.isAgentActive()` 删掉 `"resting".equals(scheduledActivity)` 死分支，简化为 `return agent.getCurrentAction() != null;`。睡觉抑制由调用处已有的 `villager.isSleeping()` 兜住，走向床由 SleepSkill 设 MOVE `currentAction` 覆盖，所以删除是安全的。

- 上次重构删了 `VillagerSchedulePlanner`，`VillagerActivitySystem.tick`（唯一写 `scheduledActivity` 的入口）也不再被调用 → `agent.scheduledActivity` **永远 null**。
- 但 `VillagerEntityMixin.isAgentActive()` 里仍保留 `"resting".equals(agent.getScheduledActivity())` 分支 —— 这是**永远 false 的死代码**。
- 后果：休息抑制（resting 时不让原版抢导航）这个契约已经悄悄断了。现在村民睡觉只能靠 `isSleeping()` 兜住；如果 SleepSkill 在"还没走到床"时没设 `currentAction`，原版 brain 会恢复、自己 walk-to-bed，与 SleepSkill 的导航**两个源抢**。
- 修：把 `isAgentActive` 的死分支删掉，改成只认 `currentAction != null || villager.isSleeping()`（其实 mixin 里 `isSleeping` 已经单独判了，`scheduledActivity` 分支直接删）。

**A2. ✅ 已修（2026-09-29）seed 资格（RoutineScheduler）与 canHandle 资格（Skill）不一致 → 死 REPEATABLE goal 无法被清除**

> 修复：`RoutineScheduler.seed()` 删掉 `case "socialize"`，让它落到 `default`（返回 null）。效果：
> - 不再种常驻 `socialize` REPEATABLE routine（前提不稳定的行为不做日常任务）；
> - `socialize` **保留在 `KNOWN_TYPES` 里**，所以 reconcile 会 evict 老存档残留的 socialize REPEATABLE goal。
> - 社交改由事件驱动：`VillagerSocialSystem.tickSocial`（相遇触发对话）+ `WorldEventBus` NEW_VILLAGER 注入一次性 goal。已确认 `BehaviorExecutor.TYPE_TO_SKILL` 仍注册 `"socialize"`，事件路径完整。

- `RoutineScheduler` 的 reconcile 只 evict「`seed()` 返回 null」的（能力/职业/配方 gate 不满足）。
- 但 skill 的 `canHandle` 是**另一个 gate**，含运行时前提（附近有没有邻居、有没有床、有没有 JOB_SITE）。两者不一致时：
  - `socialize` 是典型：`seed("socialize")` 永远 non-null（职业池里人人都有），但 `SocializeSkill.canHandle` 需要附近有村民。无邻居时 → GoalScheduler 选中 → findHandler 返回 null → NOHANDLER → 5 次（×5s=25s）abandon → 冷却 → 冷却结束又被选中 → 循环。
  - 这正是之前 live log 里「socialize 反复、村民大部分时间空转」的根因，**本次重构没解决它**（只是把 socialize 从 ONE_SHOT 换成了 REPEATABLE，循环还在）。
- 修（推荐）：**运行时前提不稳定的行为（socialize 需要邻居、trade 需要交易对象）不该做常驻 REPEATABLE，应该走「事件触发」**（`VillagerSocialSystem.tickSocial` 已按相遇触发，`socialize` routine 应删掉或降为事件触发）。退而求其次：让 NOHANDLER 的 abandon 把 REPEATABLE 冷却设得足够长（例如 1 游戏日），减少空转频率。

### B 级 —— 反应迟钝/体验差（不致命但明显）

**B1. execute 实际 5 秒一次，stuck 判定 ≈ 16 分钟、重发导航 ≈ 200 秒**

- `incrementStuckTicks()` 每次 execute +1，`GOAL_STUCK_TIMEOUT=200` → 200×5s = **1000 秒**才判 stuck。
- `cur.getStuckTicks() % 40 == 0` 重发 moveTo → 40×5s = **200 秒**才重发一次导航。
- 后果：村民导航中途被打断（被推挤、路径失效）后，会"卡住几十秒到几分钟"才恢复。
- 修：把 goal 执行的节流从"挂在 think tick 里"改成"独立每 20 tick 跑 processGoals"（让 BEHAVIOR_EXECUTOR_INTERVAL_TICKS 真正生效），或把 stuck 判定改成真实 game time（`now - action.startTick`）。

**B2. 战斗/建筑每帧 vs goal 5 秒，粒度不一致，战斗结束有 5 秒空窗**

- `tickCombat`/`tickBuilding` 每帧，goal 执行 5 秒。战斗结束时 `currentAction` 清空，下一个 5 秒边界才恢复 goal 执行 → 村民战斗完站 5 秒不动。
- 修：同 B1，把 goal 节流降到 20 tick 会顺带缓解。

### C 级 —— 性能/卫生（暂不阻塞）

**C1. `seed("craft")` 每次 reconcile 都遍历 `getUnlockedIds` + `resolveRecipe`**

- `ensureRepeatableGoals` 每 5 秒、每村民跑，`seed("craft")` → `chooseCraftTarget` → 遍历所有 unlocked id 逐个 `NativeRecipeResolver.resolveRecipe`。村民多、配方多时有 GC/CPU 压力。
- 修：把 craft 目标 item 缓存在 goal 上（已有 targetItem），reconcile 时若已有 craft REPEATABLE 就不重算；或 `chooseCraftTarget` 结果按 villager 缓存到 agent。

**C2. `currentAction` 作为原版 brain 抑制的唯一信号，契约脆弱**

- 整个"原版 brain 是否被抑制"取决于 `currentAction != null` 这一个字段。任何 skill 忘设/忘清 `currentAction` 都会导致原版 brain 错误恢复或永久抑制。
- 修（长期）：把"agent 是否接管"显式化成一个 agent 字段（如 `agent.isDriving()`），skill 不再靠 `currentAction` 隐式表达。

## 三、修复优先级（建议顺序）

| 顺序 | 项 | 状态 | 效果 |
|------|-----|------|------|
| 1 | A1 删 mixin 死分支（`isAgentActive` 简化为只认 `currentAction`） | ✅ 已修 | 消除休息抑制契约断裂 |
| 2 | A2 删 `seed("socialize")`，socialize 改事件触发（保留在 KNOWN_TYPES 仅用于 evict 残留） | ✅ 已修 | 消除"死目标空转"主根因 |
| 3 | B1/B2 goal 执行节流拆到 20 tick | 待修 | 反应从 5s 提到 1s，stuck 判定回到合理量级 |
| 4 | C1 craft 目标缓存 | 待修 | 消除每 5s 配方解析 |
| 5 | C2 agent.isDriving 显式化 | 待修 | 长期健壮性 |

**下一步建议**：B1（goal 节流拆到 20 tick）影响面最大也最能改善"迟钝"，但会改动 `updateAgent`/`processGoals` 的调用结构 —— 建议先编译验证 A1/A2，确认村民不再空转后再动 B 级。

## 四、每次改动前的自检清单（决策/执行层）

改任何 goal / skill / 调度相关代码前，逐条过一遍，能显著减少"编译—测试—返工"往返：

1. **currentAction 生命周期**：这条链路最终会设 `currentAction` 吗？结束/失败/放弃时都清了吗？（它是原版 brain 抑制的唯一信号。）
2. **两个 gate 一致性**：这个 goal 的 `seed()` gate（RoutineScheduler 资格）和 skill 的 `canHandle()` gate（运行时前提）**一致吗**？不一致 → 死 REPEATABLE goal 反复 NOHANDLER。
3. **运行时前提稳定性**：这个 goal 类型的前提（邻居/床/工作站/可交易对象）**稳定吗**？不稳定 → 应该事件触发，不该 REPEATABLE 常驻。
4. **超时用的是 execute 次数还是真实时间**：`incrementStuckTicks()` 是 execute 次数（5 秒一次），`%40` 重发导航 = 200 秒。别当成"40 tick"。
5. **是否新增了依赖 `scheduledActivity` 的逻辑**：那条链路已死（planner 已删），mixin 里 `"resting"` 分支是死代码。
6. **新 goal type 三处同步**：`BehaviorExecutor.TYPE_TO_SKILL` 注册 + `RoutineScheduler.seed` 门控 + 一个 skill 实现，漏一处就 NOHANDLER。
7. **移动是否委托 `getNavigation().moveTo`**：skill 只设导航目标 + 检查到达，别自己每帧写位置（那会和原版导航打架）。
8. **战斗/建筑是否会被 goal 抢占**：`processGoals` 里 `!ca.isGoalDriven()` 且是 ATTACK/PLACE/BREAK/FLEE/BUILD 时 return，新 skill 的动作类型别落进这个名单导致误抢占。

# 项目讲述

核对日期：2026-10-23。技术事实来自 [执行链与资源订单](事件驱动大脑与资源订单.md)，验证边界见 [实现状态](项目现状与待办清单.md)。个人职责请按实际参与范围表述。

## 30 秒介绍

这是一个 Minecraft 服务端村民智能体系统。村民根据需求、环境机会和 Utility 权重选择工作、聊天与休息，技能逐 tick 推进动作。木材和矿物供给通过资源订单连接：工人承接后采集真实方块、收集掉落并交付，以需求方实际库存判断完成。规则链路可以独立运行，LLM 为对话等交互提供可选内容。

## 展开顺序

先讲感知、候选、调度、技能、动作与结果，再用订单说明协作。A 有 2 个原木，希望库存达到 10，订单缺口为 8；B 被调度器选中供货时领取租约，检查库存和工具、寻找局部可达资源、采集并配送。若 A 只能接收 3 个，则实际转移 3 个，订单仍有缺口。需求方库存达到目标时结单。

异常处理包含缺工具补救、无资源等待、执行中断释放租约、失败冷却与有界重试。重载保存需求与职业，执行计划根据世界和库存重新建立。

## 常见追问

| 问题 | 可依据的实现 |
|---|---|
| 为什么选择 Utility？ | 当前状态修正候选得分，普通候选直接加权随机，紧急目标优先 |
| 是 HTN/GOAP 吗？ | 资源技能采用有限领域的手写条件分解，具有 HTN 思路；无通用搜索引擎 |
| 多人如何避免抢单？ | 服务端顺序检查资格与租约，一单一个有效承接者、一工人一有效租约 |
| 如何判断完成？ | 世界变化、掉落与真实库存；单批技能成功和订单满足分别判断 |
| 重启是否精确续执行？ | 资源需求保留，执行租约重新领取；世界/实体存档不保证跨文件原子提交 |
| 性能证据是什么？ | 有感知和查询预算；规模、TPS、行为分布需要实测报告 |
| LLM 断网会怎样？ | 规则工作链持续运行，村民对话具备本地回退；各 LLM 路径分别检查保护 |

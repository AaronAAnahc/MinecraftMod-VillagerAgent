# 架构反思与精简方案（VillagerAgent）

> 背景：当前存在两条行为驱动轴——`agenda → todo (AgentGoal)` 与 `schedule → scheduledActivity (mode)`，
> 两者都会尝试决定"村民现在该干嘛"，因此出现了你点出的冲突：**我在 farming mode，todo 却叫我去做工具**。
> 本文先列问题，再给精简方案，最后把本轮新增的「耕地」能力作为该方案的第一个落地样例。

---

## 一、当前架构的问题

### 1. todo 与 mode 在抢同一个裁决权（核心冲突）
- `processGoals`（每 tick）按 priority 取栈顶 `AgentGoal`，交给 `BehaviorExecutor` 派发到 skill。
- `VillagerActivitySystem.tick` 同时读 `scheduledActivity`，直接驱动 `VillagerAction`（explore / rest / craft）。
- 两套逻辑各自判断"现在干啥"，用 `getCurrentAction()` + `goalDriven` 标记做**事后仲裁**。
- 后果：`farming` 模式说"留在田里"，`craft` 类 todo 说"去做工具"——谁赢取决于代码顺序，**无语义依据**，且容易互相打断、卡死。

### 2. 双漏斗导致冗余实现
- `handleCrafting`（mode 驱动）和 `executeCraftGoal`（todo 驱动）最后都在做同一件事。
- `SleepSkill.tickRest` 是 mode 入口，`SleepSkill.execute` 是 todo 入口——同一 skill 两套入口。
- 每多一种行为，就要在**两处**写逻辑，漂移风险高。

### 3. FSM 状态落点不统一
- skill 是**单例**（所有村民共享），所以 FSM 状态不能存在 skill 对象上。
- 当前 `SleepSkill` 把进度塞进 `VillagerAction`（`ActionPhase` 只有 4 个粗状态）。
- 多步 skill（如耕地泛洪）需要更细的状态——必须有自己的 state blob，落在 `agent` 上且 NBT 可序列化，否则 chunk 卸载即丢。

### 4. agenda → goal 桥太被动
- `LongTermAgenda`（债务/交易/收购）只在**晚间反思**由 LLM 决定"现在可做"时才派生为 todo。
- 每天只触发一次；债务到期、临近时不会主动生成目标。长期承诺对行为的推动偏弱。

### 5. 设计概念边界曾被混淆（历史教训，已修正）
- config(.toml) 只放行为开关；JSON 放内容数据。
- LLM 只维护 todo 内容（Planner），执行由自主执行器按 priority 派发（Executor）。
- 一个大类一个 JSON，不拆碎。

---

## 二、精简方案：单一目标漏斗 + mode 退化为「派生上下文」

### 核心原则
**世界上只有一种"我现在要做什么"的表示 = `AgentGoal`（统一目标列表）。**
`scheduledActivity`（mode）不再直接驱动行为，改为两件事：
1. **例程目标生成器**：在 farming / resting 等时段，往目标列表里**注入 routine goal**（带 `routine=true` 语义、有生命周期窗口、到点过期而非被"完成"消费）。
2. **派生上下文**：`mode = inferModeFromCurrentGoal()`，仅供 skill 选资格、动画、对话使用——**永不作为第二个驱动源**。

### 决策流（精简后）
```
agenda ──(晚间反思, LLM)──► AgentGoal (ambition, routine=false)
schedule ──(黎明生成)─────► AgentGoal (routine, 带时间窗)
                                    │
                                    ▼
                          processGoals：按 priority 排序取栈顶
                                    │
                                    ▼
                       BehaviorExecutor.findHandler(goal)
                                    │
                                    ▼
                          VillagerSkill（单例, FSM 状态落 agent）
                                    │
                                    ▼
                          VillagerAction（原语：MOVE/CRAFT/...）
```

### 冲突如何解决
回到你的例子：**farming mode 不再"命令"村民留在田里，而是生成一条 priority=5 的 `farm` routine goal。**
若 agenda 派生出"做工具"的 todo（priority 更高），它**自然优先**——村民暂时离田去做工具，做完后 `farm` goal 仍在（routine 未被消费），自动回来继续耕作。
**没有两个驱动源互相打架，因为只剩一个目标列表、一套优先级。** 这正是「mode 退化为 routine goal」带来的直接收益。

### 待收敛项（明确承认的冗余）
- `handleCrafting` 与 `executeCraftGoal` 应合并：mode 的 "crafting" 改为生成 `craft` routine goal，执行全走 `BehaviorExecutor`。
- `SleepSkill.tickRest` 保留为「无 goal 时的兜底睡眠」，但正常路径应统一为 `rest`/`sleep` goal → skill。
- 其余 goal 类型（gather/trade/move/socialize）逐步收编进 skill，退休 `processGoals` 里的 legacy switch。

## 三、本轮落地样例：耕地能力（farming 的 tilling 缺口）

原 `FarmingAction` 只会**收获/种植**，缺**犁地**原语——被踩成 dirt 的旧耕地不会重犁。本轮按上述统一模型补齐。

### 3.1 关键判定（你的定义）
| 概念 | 判定 |
|------|------|
| 可耕作泥土 | `isTillableDirt`（dirt/grass/grass_path/coarse_dirt）**且** `hasWaterNearby`（水平 4 格内有水，即原版农田 hydration 半径） |
| 旧耕地（需维护） | 一块泥土，其 8 邻居中 **≥3 格是耕地** → 判定为被踩掉、需变回耕地 |
| 持有锄头 | `agent` 库存含 `HoeItem`（农民起始物品已含 `IRON_HOE`） |

### 3.2 耕地 action 原语（`FarmingAction` 新增）
- `tillBlockAt(villager, world, agent, pos)`：持有锄头时把泥土设为 `FARM_LAND`（moisture=7 即湿润），并装备锄头做视觉展示。
- `approachTarget(...)`：通用的「走到目标再动作」状态机，使用 `farmMove` 标记的 MOVE action，让 farm skill 能识别自己的进行中移动。

### 3.3 两个 skill（都实现 `VillagerSkill`，注册进 `BehaviorExecutor`）
- **`FarmMaintainSkill`**（维护旧耕地）
  - 触发：`farm` goal 且 `farmMode=="maintain"`，或纯 `farm` goal 但附近确有 reverted farmland（机会式）。
  - 行为：每 tick 找最近的 reverted farmland → 走到 → 犁；找不到则完成 goal。routine 生成器会在下个 farming tick 重建它。
- **`FarmReclaimSkill`**（开辟新耕地）
  - 触发：`farm` goal 且 `farmMode=="reclaim"`。
  - 行为（状态机）：
    1. **PLAN**：取最近的可耕作泥土为起点（天然靠近水源），BFS 向外泛洪收集可耕作地块，直到标记 **N** 块为待开垦；**N 为每次执行随机生成**（`4 + random(7)`，即 4~10），代表本次开垦多少地。
    2. **TILL**：逐个走到待开垦块、犁掉、从 pending 移除，直到清空 → 完成 goal。
  - 状态落点：`FarmReclaimState`（per-村民、NBT 序列化），存 N、pending 列表、已犁计数——chunk 卸载/重启不丢。

### 3.4 接入（体现「mode 生成 routine goal」）
- `VillagerAgentManager.ensureFarmRoutineGoal`：在 `scheduledActivity=="farming"` 时，若无 `farm` goal 且当前无 farmMove 动作，则按上下文生成一条 `farm` goal（`maintain` 若有旧耕地，否则 `reclaim`），priority=5、importance=6。
- `performFarmerActions` 对 `farmMove` 动作**让路**（不再被现有收获/种植扫描打断）。
- `processGoals` 中对 `farm` goal **不清除** `scheduledActivity`（否则 routine 无法自我重建）；其余 goal 仍照旧清除。

### 3.5 验证要点（你本地编译后看日志）
- 农民站在一片旧耕地旁 → 应自动把 reverted 泥土犁回耕地。
- 农民附近有水源+泥土 → 应随机开垦 4~10 块新耕地（日志含 `Tilled ... into farmland`）。
- 若 agenda 产生更高优先级 todo，耕作应让路、完成后再继续（冲突消失）。
- 重启游戏 → `ReclaimState` 应被持久化，开垦进度不丢。

---

## 四、结论
冲突的根因不是"todo 和 mode 哪个对"，而是**有两个驱动源**。把它们合并成单一目标漏斗、让 mode 退化为 routine 目标的生成器与派生上下文，冲突在结构上消失。本轮耕地能力按此模型实现，可作为后续 `CraftSkill`/`MoveSkill`/`TradeSkill` 收编的模板。
